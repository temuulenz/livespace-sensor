# Phase 1 architecture

Platform Activity + XML dashboard → CameraController → Camera2 rear camera → ImageReader YUV_420_888.

MainActivity owns explicit Start/Stop, permission requests, TextureView, settings, diagnostics and a one-second UI refresh. DeviceMonitor reads sticky battery state, available RAM and connectivity. CameraController owns a HandlerThread, CameraDevice, capture session, preview Surface and two-image ImageReader. Every available latest image is drained and closed. Sampling is throttled (default 1000 ms); Phase 1 only counts samples and logs dimensions, without pixel processing or storage. No inference latency is invented.

640×480 is preferred from the intersection of advertised YUV and TextureView sizes; otherwise use a supported smaller size, then smallest common size. Camera errors close resources and expose an explicit Start retry. Screen transitions stop capture; no automatic background operation, wake lock or service yet. Camera permission alone is requested; microphone permission belongs to Phase 3. Preview can be disabled while retaining local YUV acquisition.

Settings persist validated non-secret device/location IDs, frame sampling interval and local preview preference in private SharedPreferences. Future transport/AI/audio settings remain explicitly unavailable. No networking permission, network client, raw recordings, model assets or offline telemetry queue exists in this phase.

UI and diagnostics use real Android APIs. Network connected does not imply server connectivity. Uptime is the current foreground capture attempt, reset on Start; errors end that attempt. Frame counts indicate acquisition, not person detections.

Privacy deployment prerequisites: venue permission, visible notice and informed consent as applicable, camera positioning limited to approved monitoring areas, no private spaces, physical device security and isolated IoT networking. Operators must review applicable requirements before deployment. Phase 1 is an engineering preview, not an unattended deployment.

# Phase 2 extension

CameraController now hands each acquired Image to InferenceScheduler on the camera worker. The scheduler checks initialization, interval and a single atomic in-flight flag. It converts only a sampled 300×300 RGB grid into its reusable direct buffer on the camera worker, then submits exactly one invocation to a dedicated inference HandlerThread. The caller closes the Image immediately after preparation; inference never retains Image/planes. Full frames are neither copied nor queued. Interval checks happen before preprocessing; busy frames are discarded. There is no unbounded executor queue.

PersonDetector owns the memory-mapped asset and Interpreter on the inference worker, validates the model contract, and reuses output arrays/maps. Built-in CPU kernels only (NNAPI and XNNPACK disabled). Stop first disables future work, then queues interpreter close behind any invocation. Activity generation checks ignore stale results/status. Camera cleanup runs on its owner worker and stale session callbacks check thread identity; TextureView buffer release is deferred until camera close completes, without UI-thread joins. Native mapped model memory is reclaimed after interpreter close and the session becomes unreachable; repeated initialization is tested but no zero-RSS-on-close claim is made.

DetectionResult holds only boxes/scores, observed count, completion UTC timestamp, acquisition elapsed time and stage timings. OccupancyTracker uses the upper median of up to five recent valid raw counts; it does not associate identities or add counts across frames. No inference means unavailable, not zero. Results become stale after max(2×interval, 5 seconds); stopped or differently rotated results are not shown as current. Confidence is the arithmetic mean of the current retained-person scores, null for no detections, independent of the temporally smoothed count.

FrameGeometry defines inverse rotation for preprocessing and a fit-center rectangle shared with preview and DetectionOverlayView. The entire upright field is resized to square model input. Boxes are mapped back by normalized coordinates into the upright letterboxed preview; ROI filtering uses box centers. No extra NMS follows the model's built-in detection postprocess.

Dashboard settings persist validated detection threshold, interval, CPU threads (1/2/4), box visibility and normalized monitoring area. Defaults: threshold 0.5, 3000 ms, 2 threads. Benchmark overrides are accepted only when the package is debuggable and do not persist. Sensor readings remain local; no service, audio, transport or offline queue is introduced.

# Phase 3 acoustic monitoring and snapshot

AudioMonitor adds a dedicated owner thread beside Camera2 and TFLite; neither AI dependency nor inference/preprocessing implementation changed. Microphone monitoring is optional (default enabled), requests RECORD_AUDIO, and is limited to the foreground sensor session. Runtime denial leaves camera inference available. Capture errors clear acoustic data and expose an error without stopping AI. Stop/Home disables capture, interrupts a short polling wait, and the owner stops/releases AudioRecord in finally; the UI never races release against a blocking native read or joins an audio thread.

AudioRecord uses API 23 READ_NON_BLOCKING, mono PCM16, a reusable 100 ms ShortArray and a 20 ms polling wait. It prefers 16000 Hz, then tries 44100, 48000 and 8000 Hz if initialization fails. Native buffer bytes are even-aligned and at least twice getMinBufferSize and 500 ms of mono PCM16. VOICE_RECOGNITION is preferred, MIC is an explicitly displayed fallback. The source choice does not prove the vendor disables every gain/processing effect. No UNPROCESSED (API 24) or new dependency is required. Reference: [AudioRecord](https://developer.android.com/reference/android/media/AudioRecord), [audio sources](https://developer.android.com/reference/android/media/MediaRecorder.AudioSource).

NoiseProcessor consumes only the successfully read PCM prefix and publishes exact one-second sample windows. Normalized RMS = sqrt(mean((sample/32768)^2)); dBFS = 20 log10(RMS), clamped at a documented −120 dBFS numeric floor. This floor is not microphone precision or an SPL reading. A 30-window ring averages linear mean-square energy before converting to dBFS; its peak is the largest absolute PCM sample over the same rolling windows, not peak-window RMS or physical sound-pressure peak. Startup uses the available number of windows, displayed explicitly. PCM is discarded/reused immediately and never saved, logged or transmitted. Only aggregates reach UI/history/snapshot.

Optional manual SPL calibration is disabled by default. A finite configured offset in [−200,200] dB gives estimated SPL = dBFS + offset. The operator must obtain offset = reference-meter SPL − simultaneous measured dBFS under fixed gain, source and placement. Zero/floor-limited input has no SPL estimate even when calibration is enabled. No A-weighting, frequency correction, certified meter equivalence or calibrated accuracy is claimed. The digital values remain labeled dBFS; estimated SPL is a separate nullable value.

At the Phase 3 boundary, MainActivity published to TelemetryRepository.store. TelemetryStore synchronizes producer updates and returns an immutable SensorSnapshot with UTC epoch milliseconds, smoothed observed people, confidence, inference latency, RMS, dBFS, nullable estimated SPL/calibration, battery metrics and producer timestamps. Detection expires after max(2×interval, 5 s), audio after 3 seconds and battery after 30 seconds using monotonic age. Stop clears observations before late callbacks can publish; generation checks reject those callbacks. Phase 4 now consumes this snapshot through the v1 transport described below.

The dashboard's existing one-second refresh displays acoustic data and updates a bounded 60-window RMS dBFS graph. Audio callbacks update immutable state rather than driving a second dashboard refresh timer. Settings retain device/location/detector/preview controls and add microphone enable, calibration enable and offset. TFLite remains pinned at 2.8.0 with the original UINT8 model; defaults remain two threads, 3000 ms, threshold 0.5.

# Phase 4 preview and transport

The rear-camera TextureView receives the sensor-orientation correction from Android's texture consumer; the Activity adds the display-rotation transform only once. Fit-center size uses the upright dimensions for sensor-minus-display rotation, and the detection overlay shares the resulting rectangle. YUV preprocessing retains the existing sensor-minus-display model rotation, so display orientation does not alter the model's raw frame contract. Visual box alignment remains a phone-side manual check.

`SensorProtocolV1` is the sole serializer/parser and follows frozen `docs/SENSOR_PROTOCOL.md`. OkHttp 4.12.0 connects off the UI/camera/audio/inference workers with an Authorization Bearer header and standard TLS. A valid `sensor.ready` matching configured IDs and `dataSource=real` gates telemetry. A 30-second OkHttp RFC control-frame ping interval detects dead peers; automatic pong handling remains enabled for server-originated pings, and a missed pong enters the normal reconnect/backoff path. No application heartbeat JSON is sent. The actor serializes queue/state mutations and telemetry ticks. Production service injects the Phase 6 app-private SQLite outbox; protocol tests may inject a bounded in-memory queue. Both retry unchanged payload bytes and message IDs.

Tokens are AES-GCM encrypted with an API 23 AndroidKeyStore key; only ciphertext/IV are in private preferences. Endpoint validation requires explicit private-IP ws opt-in, rejects URL credentials/query strings and never modifies TLS validation. The current service/outbox ownership supersedes the earlier Activity foreground-only description below.

# Phase 5 foreground runtime

`SensorService` is the continuous runtime owner. It is started explicitly by the user, runs as a foreground service with a persistent Stop action, and is not restarted at boot (`START_NOT_STICKY`, no boot receiver). Activity binding is observational; TextureView is an optional surface, not the analysis owner. TextureView destruction on the Note 4 triggers a CameraDevice close/reopen around the changed surface set because in-place capture-session reconfiguration is unreliable on its Exynos Camera HAL1. ImageReader, inference and audio owners stay in the service. The partial wake lock is held only during the explicit running session and is released after owner cleanup. See [PHASE5_REPORT.md](PHASE5_REPORT.md).

# Phase 6 durable outbox

`SensorWebSocket` uses the shared `SqliteTelemetryOutbox` in app-private `sensor_outbox.db`. The queue records only immutable protocol-v1 JSON, original message ID/time and identity scope. Rows are inserted before send and removed after matching `accepted`/`duplicate` ACKs only. `sensor.ready` gates replay and device/location are checked for both readiness and each selected row. The default limits are 10,000 messages and 24 hours; settings can reduce either. Queue retention/overflow/rejection counters persist. Backlog is bounded to four in flight, sent at one per second, and fresh live data takes priority over older backlog. It never stores raw media. See [PHASE6_REPORT.md](PHASE6_REPORT.md) and [SENSOR_PROTOCOL.md](SENSOR_PROTOCOL.md).

## Phase 7 API 23 production TLS compatibility

The Note 4 lacks ISRG system trust anchors. Production WSS now uses app-bundled, fingerprint-verified ISRG Root X1 through platform path validation only on API 23 and the exact production endpoint; default hostname checks remain enabled. Other endpoints/newer Android retain system TLS defaults. Physical trust-anchor failure, corrected TLS 1.2, negative certificate/hostname checks, authenticated ready/accepted ACKs and public real-source updates were verified. See [PHASE7_TLS_COMPATIBILITY.md](PHASE7_TLS_COMPATIBILITY.md) for provenance, implementation, tests, evidence and remaining Phase 7 checks.
